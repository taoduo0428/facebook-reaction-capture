Proxyman是什么

---


**OpenAI Codex**

Proxyman 是一个带图形界面的 HTTP/HTTPS 抓包代理工具，功能类似 Charles、Fiddler、Burp Suite 和 mitmproxy。

基本流程是：

```text
手机或模拟器中的 App
→ 把网络代理设置为 Proxyman
→ Proxyman 接收请求
→ 转发到目标服务器
```

安装并信任 Proxyman 的 CA 证书后，它可以解密经过自己的 HTTPS 流量，展示请求 URL、Header、Body 和响应内容。

但它有两个重要限制：

- App 流量必须真正经过 Proxyman。
- App 如果使用 SSL Pinning、原生网络通道、QUIC 或绕过系统代理，Proxyman可能只能看到连接，甚至完全看不到请求。

我们项目里主要使用的是 mitmproxy。两者原理类似，但 Proxyman偏图形界面操作，mitmproxy更适合脚本化、自动保存和批量解析。

**问题点：** 模拟器重启后可能需要重新 `adb root`；如果 tcpdump 启动晚了，前面的握手和请求会丢失；如果流量没有经过 `18081`，该过滤器也抓不到。

**成功标准：** tcpdump PID 存活，远端 PCAP 持续增大。这里的内容是 TLS 密文，不会直接出现用户名、GraphQL 正文。

### 3. 建立 ADB reverse 映射

**做什么：** 让模拟器访问自己的 `127.0.0.1:18081` 时，实际连接电脑的 `18081`。

**如何实现：**

```text
adb reverse tcp:18081 tcp:18081
adb reverse tcp:7897 tcp:7897
adb reverse tcp:8081 tcp:8081
```

脚本安装映射后再读取 `adb reverse --list` 验证，见 [facebook_transport.ps1](/C:/Users/lenovo/Desktop/facebook/facebook_transport.ps1:194)。

**问题点：** ADB 重连或重启后映射会丢；只有设置 Android 代理、没有 reverse，模拟器的 `127.0.0.1` 不等于电脑的 `127.0.0.1`。

**成功标准：** reverse 列表中明确存在 `tcp:18081 -> tcp:18081`。

### 4. 启动 mitmproxy 解密链路

**做什么：** 在电脑 `18081` 接收模拟器流量，实时读取解密后的 HTTP，再通过 Clash 转发给 Facebook。

**如何实现：**

```text
mitmdump
  --listen-port 18081
  --mode upstream:http://127.0.0.1:7897
  -s facebook_capture_addon_safe.py
  -s facebook_raw_flow_writer.py
```

参数组装在 [run_facebook_capture.ps1](/C:/Users/lenovo/Desktop/facebook/run_facebook_capture.ps1:689)，原始 HTTP flow 写入逻辑在 [facebook_raw_flow_writer.py](/C:/Users/lenovo/Desktop/facebook/facebook_raw_flow_writer.py:68)。

**解密原理：** Facebook App 与 mitmproxy 建立一条 TLS；mitmproxy 使用模拟器已信任的 CA 动态签发站点证书。随后 mitmproxy 再与 Facebook 建立另一条 TLS，因此它能在中间读取 HTTP。

**问题点：** CA 未信任、证书固定、端口被占用或上游 Clash 不通，都会导致没有解密流量。Proxyman 看不到请求，常见也是代理没真正经过它、CA 不被 App 接受、reverse 缺失，或者列表数据已缓存而没有产生新请求。

**成功标准：** mitmdump 不提前退出，`18081` 正在监听，并开始产生 flow。

### 5. 将模拟器切换到抓包代理

**做什么：** 把 Facebook App 的 HTTP 代理从正常出口 `7897` 临时切换到 MITM 的 `18081`。

**如何实现：** 先写 capture marker，再执行 Android global proxy 设置，并回读确认。代码见 [facebook_transport.ps1](/C:/Users/lenovo/Desktop/facebook/facebook_transport.ps1:232) 和 [run_facebook_capture.ps1](/C:/Users/lenovo/Desktop/facebook/run_facebook_capture.ps1:734)。

**问题点：** 如果先启动 App、后切代理，早期请求会漏；watchdog 如果不知道正在抓包，可能把代理自动恢复为 `7897`。

**成功标准：** Android 返回的代理值严格等于 `127.0.0.1:18081`，capture marker 有效。

### 6. 严格打开目标帖子

**做什么：** 保证后续 reaction 用户确实来自指定帖子，而不是 Facebook 保留的旧页面或推荐帖子。

**如何实现：** 停止 Facebook App，建立新的 JSONL 行号边界，再通过 Android VIEW intent 打开准确 URL；必要时使用本地 ID 到 URL 映射或精确 ID 搜索。然后只分析边界之后的新 GraphQL 响应，并要求目标 ID/URL 匹配。见 [open_facebook_post_readonly.ps1](/C:/Users/lenovo/Desktop/facebook/open_facebook_post_readonly.ps1:247)。

**问题点：** 页面显示正确不代表网络响应正确；App 可能保留旧 story surface；分享短链可能重定向；搜索可能点进同名或错误结果。

**成功标准：** `target-open-diagnostics.json` 为 `verified=true`，分析器返回 `matched`。失败时最多严格重试三次，不允许带着目标不确定状态继续。

### 7. 打开 reaction 列表并做初始探测

**做什么：** 找到 reaction 数字或图标，打开用户列表，确认列表加载完成，并判断当前账号是否真的能拿到用户节点。

**如何实现：** 先在严格目标详情中找 reaction 入口；找不到时进入评论详情并向上揭示帖子摘要。打开后等待页面从 `reaction-list-loading` 变为 `reaction-list`，再检查新请求的 `source_post_id` 是否唯一且等于目标。逻辑见 [explore_facebook_readonly.ps1](/C:/Users/lenovo/Desktop/facebook/explore_facebook_readonly.ps1:2103)。

**问题点：**

- `query_records=0`：入口没触发请求，或者列表使用了缓存。
- 有 query、没有用户：当前账号可能只能看到数量，不能枚举姓名。
- source ID 不一致：进入了错误帖子，立即停止。
- 页面一直 loading：网络、会话或 App UI 状态异常。

**成功标准：** screening 为 `enumerable`，`probe_status=initial-ready`，并且已经出现至少一个目标帖 reactor 用户节点。

### 8. 对 ALL reaction 流自适应分页

**做什么：** 持续下拉 reaction 用户列表，直到服务端明确返回最后一页。

**如何实现：** 初始列表就是 `__ALL__` 流，而且每个用户节点带有自己的 reaction 类型，所以优先分页 ALL，不重复点击 Like、Love 等分类。本次全量参数是初始预算 60、绝对上限 0、burst 2、分类 tab 数 0。

`ReactionAbsoluteCap=0` 不是只抓 60 次，而是：只要连接仍为 open 且近期有增长，就按块扩展预算，直到 terminal。核心循环见 [explore_facebook_readonly.ps1](/C:/Users/lenovo/Desktop/facebook/explore_facebook_readonly.ps1:978)。

**分页判断：** 每次滚动后轮询 `facebook-live-progress.json`，比较 query 数、页数、用户数和最新行号；`has_next_page=true` 表示还能继续，`false` 表示最后一页。

**问题点：** 无增长时依次切换长滑、短滑、回弹、等待等策略；看到加载器时停止继续滑动，等待响应；限流则退避，本次配置连续一次限流就停止；会话限制、目标错位也会立即停止并保留部分数据。

**成功标准：** ALL 流出现 `has_next_page=false`，停止原因是 `terminal`，不能把“预算用完”或“暂时不增长”当作完整。

### 9. 同时保存三层抓取证据

这一步贯穿第 6 至第 8 步。

- [raw-network.pcap](/C:/Users/lenovo/Desktop/facebook/runs/reaction-full-smoke-20260902-120331/raw-network.pcap)：模拟器网络栈中的 TLS 密文。
- [raw-facebook-http.mitm](/C:/Users/lenovo/Desktop/facebook/runs/reaction-full-smoke-20260902-120331/raw-facebook-http.mitm)：mitmproxy 实时解密后保存的完整 HTTP flow，可能包含敏感会话数据。
- [safe-facebook-http-capture.jsonl](/C:/Users/lenovo/Desktop/facebook/runs/reaction-full-smoke-20260902-120331/safe-facebook-http-capture.jsonl)：去掉 Cookie、Authorization、token 等字段后的分析输入。

安全 JSONL 的脱敏和写入在 [facebook_capture_addon_safe.py](/C:/Users/lenovo/Desktop/facebook/facebook_capture_addon_safe.py:757)。

### 10. 解析、标准化和去重

**做什么：** 从 GraphQL 响应中提取用户，并形成稳定 CSV。

**如何实现：** 解析器只处理 `FeedbackReactorsGraphService*` 响应，兼容连续 JSON 文档，以及 `reactors`、`important_reactors`、`friend_reactors` 等结构。随后统一提取 ID、姓名、头像、reaction 类型和源帖 ID。见 [analyze_facebook_capture.py](/C:/Users/lenovo/Desktop/facebook/analyze_facebook_capture.py:817)。

**去重规则：** 以 `(source_post_id, user_id)` 为主键；缺少 ID 时才回退到姓名。相邻 GraphQL 页可能重叠，所以原始节点数通常高于唯一用户数。

**问题点：** 不按源帖隔离会混入其他帖子；只按姓名去重可能误合并同名用户；只统计 CSV 行数而不检查分页终点，无法证明抓全。

**成功标准：** 生成 [facebook-reactor-users.csv](/C:/Users/lenovo/Desktop/facebook/runs/reaction-full-smoke-20260902-120331/analysis/facebook-reactor-users.csv)，且唯一键无重复、源帖唯一、JSONL 解析错误为 0。

**成功标准：** 刚才重新运行 full gate，返回 `passed=true`、3539 个唯一用户、143 页、terminal，140 次增长、282 次滚动、用时约 303 秒。

**问题点：** 如果抓取成功但 PCAP 拉回失败，不能说三层证据完整；如果直接杀进程而不等待刷新，文件尾部可能缺失；代理没恢复会影响后续 Facebook 使用。

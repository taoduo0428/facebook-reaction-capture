### 4. 恢复有误放行，也有误阻塞

新 `_identity` 对缺 PID 且未明确 stopped 返回 absent。`plan` 对 active job 只拦 match/unknown，mismatch 也能进入 requeue/cancel 分支。终态或已丢失的 job 即使曾有遗留 PID，其 lease 分支把 identity 固定为 absent。未核对 cleanup 及结果写失败，`apply` 会清除 requeue 的 pin。相反，显式 `stopped` 的 active job 可以被 requeue，但其 lease 检查只列 absent/none，从而留下原租约。plan 还只取最多 10,000 条 active jobs，恢复应遍历完整集合。[计划:109](../../facebook_backend/scheduler/recovery.py#L109) · [租约:144](../../facebook_backend/scheduler/recovery.py#L144) · [身份与 apply:191](../../facebook_backend/scheduler/recovery.py#L191)

## 最小安全切换路径

1. **先切断双派发可能。** 为现有 manager 分开“恢复/查询”与“启动后台线程”，统一所有启动器选择，默认沿用旧路径。停领后 join 旧线程，明确谁拥有队列。所有权不明、旧 runner 未确认退出、pending transport 或持久化阻塞时不启动新派发器。仅关闭新提交不够。
2. **只切状态存储。** 用隔离副本对齐 batch commit、所有恢复字段、状态事件和幂等，检查 schema head，再验证 manifest → DB → 新空 manifest 目录逐项往返。离线核对无 orphan/冲突/未解释的 skip。运行模式始终只有一个写者，先保留旧调度和严格结果门禁。
3. **接通受控执行协议。** 先接两个回调、attempt 目录、timeout、取消、双平台 cleanup、结果持久化与 SHA 元数据。每个结果写检查当前 owner/token/attempt。确认停止、清理、持久化三者齐备后才允许释放。失败时可见、可重试核验，不能仅凭 TTL/cooldown 接管。
4. **先观察决策，再切一次派发。** 在无设备假 runner 与临时库用旧、新规则并排比较，观察方不 claim、不写、不执行。通过重复 tick、重启、lease 跨期、存储故障、两设备争抢的用例后，演练停机替换为单 Scheduler。保留单 active、Uvicorn 1；旧 loop 启动计数为零、新 loop 为一。Docker 的只读控制面须单独证明不会启动/恢复执行。
5. **回退须携带新状态。** 先停接单、停 claim，等待/确认当前进程树、代理、反向映射、watchdog 和 lease/写入均有结果，备份一致状态（SQLite 含 WAL 的一致性备份）。导出至空目录，逐项核对状态、attempt、批次顺序、幂等/清理字段和摘要，再只启一个旧 writer。保留原数据和差异清单。只改环境变量或只回退 Git 会遗漏切换期间任务。
6. **分别签收真实平台。** CI 与无设备用例之后，由主会话组织 Windows、真实 macOS/Android 按五类 URL 验收完成范围、产物和清理。不更改稳定等待、版本或登录态作为迁移手段。本审计未操作设备、服务、已有配置、数据目录或索引。
